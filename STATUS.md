## SESSION 7 — ANIMATION SPEED FOUND (block[11], inverted). CORRECTION: my earlier
### "speed is not controllable" conclusion was WRONG (user pushed back, and was right).

### The answer
- Animation SPEED = **block[11]** of the 0x02 settings block (NOT block[5]).
- On this firmware it is **INVERTED**: 0 = fastest, higher = slower (0..255 usable).
- block[5] = animation **DIRECTION** (0-3) — confirmed 3x by the user watching.
  The official driver mislabels block[5] as "speed"; on this SK61L firmware that byte
  is direction, so the official app's speed slider would change direction here.
- App-level speed is 0..100 with 100 = fastest (natural), mapped to the inverted
  firmware byte by speedToFw()/speedFromFw() in protocol.js.

### How it was found (scripts in re/)
- Official driver writes speed ONLY to block[5] -> dead end (that byte is direction).
- Live-probed every other candidate byte (5,6,7,8,9,20,82,83,127): none changed speed.
- Setting the whole untested header gap [10..19,21..23] = 30 DID slow the animation.
- Bisected byte-by-byte (re/probe_bisect2.py) -> block[11]. CONFIRMED by user.
- PITFALL: re/probe_bisect.py did NOT restore between its two windows, so the
  "second half" window was contaminated by the first half. Always restore between
  probe steps.
- The official app's speed slider is therefore useless on this keyboard for the
  hardware-effect system; only the software-rendered (SpecService) effects in the
  official app have a real speed control.

### App changes (user-verified working)
- app/renderer/index.html: Direction slider = #fxDirection (0-3); NEW #fxSpeed (0-100).
- app/renderer/js/protocol.js: speedToFw()/speedFromFw() helpers (SPEED_FW_MAX=255);
  writeLighting now writes block[5]=direction, block[11]=speed; verify-after-write
  checks both bytes.
- app/renderer/js/app.js: lighting.direction + lighting.speed fields; config v1->v2
  migration (v1's "speed" key was really the DIRECTION value); connect sync reads
  block[5] and block[11].
- Verified live: app-level speed 66 -> firmware byte 87 -> animation slower;
  count=255 confirms it is committed to flash (survives reboot like the colours).

## SESSION 5 — FLASH PERSISTENCE SOLVED (the goal of this project)

### THE BREAKTHROUGH: block[126] (custom-count) = the keyboard's SAVE SWITCH
- **Changing block[126] commits the ENTIRE settings block (cmd 0x02) to FLASH**:
  palette + effect + brightness + flags. Proven by `re/flash_trigger_bisect.py`:
  - Stage A: blue palette + count 255→1, then profile-bounce (which ALWAYS reverted
    palette before) → **PERSISTED IN FLASH**.
  - Stage A2: count 1→255 (clean factory value) → **PERSISTED IN FLASH** (clean state).
  - User unplugged the keyboard **TWICE** → blue survived both times. DEFINITIVE.
- **Why every old test "reverted":** all of them left count at 255 (no change →
  no commit). test_flash_persist / calibrate10 / test_commit_01 all did this.
  The 3b "hardware fact" was WRONG — commits are trigger-gated, not impossible.
- Trigger details (observed): count→1 commits; count→255 commits; count→0 does NOT
  appear to trigger (clear_customflag 1→0 didn't commit). Use only the 1↔255 ping.
- Commit is INSTANT (custom test committed within ~1s of the count change — that's
  why its readback after bounce showed effect 15).
- **App integration DONE**: `protocol.js writeLighting()` now does the 2-write ping
  (count=1 → write, count=255 → write) + verify `count===255`. Every Apply button
  = colors saved to flash = survive reboot/power loss with NO app running.
- Auto-apply-on-start + autostart stay OFF — no longer needed for colors.
- OPEN QUESTION: do key remaps (cmd 0x03) and macros (0x05) persist natively?
  Not yet power-cycle tested. Final reboot test should check one remap too.

### Custom-LED black incident — TRUE ROOT CAUSE (corrects session 4)
- My test_custom_green / fix_custom_white packets were **MISALIGNED by one byte**
  (built pkt[1]=cmd then prepended another 0x07 → cmd landed at wire index 2 →
  firmware saw cmd 0x00 → IGNORED). **Custom buffers 0x08/0x09/0x0A were never
  written.** Session 4's "custom-LED store is flash-backed" was a MISDIAGNOSIS —
  custom data was never successfully written at all (still unknown whether that
  region is flash-backed; likely never needed now).
- The BLACK came from block **effect=15 + count=1** (that write WAS aligned) with
  NO custom data behind it → custom mode rendered empty → black.
- **It survived unplug because count 255→1 = the save switch** → block committed
  effect15+count1 to flash. Later restores wrote effect0 to RAM but left count
  changed only 1→0 (not a trigger) → no commit → bounce kept reloading
  effect15+count1 from flash → stayed black. Boot = init-rainbow flash then
  custom-black. Matches every observation.
- **factory_reset.py (0x01 0xFF) = THE recovery** — fw restores flash to factory ✓.
- Correct custom-LED packet format (from official SetCustomLED, MK61Series.js 639):
  `send([cmd, profile, customNum, 0,0,0,0,0] + payload256)` — 7-byte header, then:
  color 0x08 = planar R/G/B × 70; frame 0x09 = [0]=count, key bits at [1+frame*9+g],
  times at [182+f*2]; effect 0x0A = planar effect/speed/breath, 2=static.

## SESSION 4 — CUSTOM-LED FLASH TEST (both proves persistence AND recovers lights)

### RESULT: custom-LED store IS flash-backed (proves the user's hunch)
> **CORRECTED IN SESSION 5 — this conclusion was a MISDIAGNOSIS.** The custom
> buffers were misaligned (never written); what survived unplug was the settings
> BLOCK, committed by the count-field change (effect15+count1 = the save switch).
> See session 5 for the true root cause. Keep the recovery steps below.
- Attempted static-green via custom-LED path: 0x08 color + 0x0A effect + block effect 15.
- Lights went BLACK. Critically, the black state **survived a full unplug/replug**.
  => A RAM-only experiment would have reverted to factory rainbow on power loss.
  => The black persisting PROVES the custom-LED store is written to FLASH.
  => This answers the user's original question: "is there generally no way to save
     to flash?" YES — via the custom-LED path (effect 15). It's just static per-key
     colors, not the animated rainbow wave.
- Why it went black: my test sent color (0x08) + effect (0x0A) but NEVER sent the
  frame buffer (0x09). Without frame data the LED engine has no per-key frame map
  to render -> renders nothing -> black. See official SetCustomLED (MK61Series.js
  639-776) which sends all three: color 0x08 -> frame 0x09 -> effect 0x0A in sequence.

### RECOVERY that worked (record for future)
- **factory_reset.py = THE proven recovery.** Sends factory-reset cmd (0x01 0xFF),
  waits, then profile-bounces (switch to profile 2, back to profile 1) to force the
  LED engine to reload. Ran clean -> block came back effect0/bri10/LED on. User
  confirmed: "the reset script fixed it". Use this FIRST if lights are ever stuck.
- fix_custom_white.py also ran (overwrites custom slot 0 with a complete valid set:
  color all-white 0x08 + ONE frame covering all 70 keys 0x09 + static effect 0x0A,
  then sets block back to effect 0). This is the correct way to make custom mode
  RENDER properly (vs my broken test that omitted the 0x09 frame -> black).
- LESSON: to exit a stuck custom-LED state, run factory_reset.py. To make custom-LED
  mode actually display, you MUST send all three buffers (color 0x08 + frame 0x09 +
  effect 0x0A) — omitting the frame buffer 0x09 renders black.

### PERSISTENCE CONCLUSION (settled, do not re-derive)
- Animated palette (effect 0-12, cmd 0x02, block[84..125]): RAM-only. Cannot persist.
  Proven by unplug + profile-bounce tests. Official app re-pushes from local DB each launch.
- Custom-LED per-key mode (effect 15, cmds 0x08/0x09/0x0A/0x07): PERSISTENT / flash-backed.
  Proven by black state surviving full power-cycle this session. Tradeoff: static colors,
  not animated wave/breath. CustomDataDB.db was empty for MK61L before this test.
- => TRUE no-software permanent colors ARE possible via custom-LED mode. The app's
  Apply could write BOTH: animated palette (for live preview) + custom-LED slot (for
  flash persistence). Custom mode = the "it survives reboot with no app running" option.

### 2. Firmware facts (confirmed)
- Brightness (byte 4): valid 0..20. Past 20 it corrupts the animation.
  - App slider max changed 31 -> 20 (index.html) and write cap 31 -> 20 (protocol.js).
- byte 5 = DIRECTION/orientation, NOT speed (0..3). Slider label changed to "Direction".

  Currently reads 2 in user's stored block.

### 3. TWO separate lighting systems in the official driver (KEY INSIGHT)
- **Effect mode** (effect ids 0..12, incl. Wave=0): driven by the 256-byte settings
  block via cmd `0x02` (read cmd `0x82`). Wave palette at block[84..125], **14 colors**.
  - **SOLVED (ground truth): palette is PLANAR with n=14 for Wave.**
    R plane = block[84..97], G plane = block[98..111], B plane = block[112..125].
  - Proof: launched official MK Series app, user set all 14 slots to red, dumped the
    block. Red appeared as one contiguous high-R block at 84-97, then low G, then low B
    (interleaved scrambled it into white/lavender). Official driver writes PLANAR
    (MK61Series.js lines 1475-1477: R at off+0, G at off+n, B at off+2n).
  - **Live-confirmed**: planar-14 GREEN turned the WHOLE keyboard green (re/test_planar14_green.py).
  - Driver's `arrColorNum[0]=8` is STALE for this 2021 firmware — the real count is 14
    (matches the official UI, which shows 14 slots). Do NOT use 8.
  - `app/renderer/js/keycodes.js`: Wave colors changed 8 -> 14.
  - `app/renderer/js/protocol.js` + `app.js`: write + read-sync both PLANAR n=14.
  - Driver reads with an off-by-one bug (`rtnData[8+i-1]`, line 1439) but writes to
    `8+i`. We correctly use [8..263] for both (find_offset.py: block[4]=bri at raw[12]).
- **Custom per-key mode** (effect id 15 = "Custom Mode"): 432-byte per-key buffer
  sent via cmd `0x07` (SendLEDData2Device, MK61Series.js line 1604; SetLEDMatrix
  line 1571). This is the "16 million colors" path. Only runs when bSetSyncEffect.
  - This is the UNTESTED candidate for live color changes.
